# Convertible Deposit Retuning: Implementation Review

## Scope

This proposal changes the USDS Convertible Deposit auction to a three-month term, a
100 USDS minimum bid, a 10,000 OHM standard tick, a 0.10% price increment and a
0.10% base emission rate. Three-month early reclaim becomes 90%.

The implementation is `src/proposals/ConvertibleDepositRetuningProposal.sol`.
Its simulator and regression tests are in
`src/test/proposals/ConvertibleDepositRetuningProposal.t.sol`.
The human-readable proposal description is generated by the implementation's
`description()` function, not maintained as an independent copy.

## Actions and unchanged controls

| Setting | Target | Effect |
| --- | --- | --- |
| Offered term | 3 months only | Queued until the next auction update |
| 3-month reclaim | 90% | Immediate shared-rate change |
| Minimum bid | 100 USDS | Immediate |
| Price increment | 0.10% | Immediate; encoded as 10010 |
| Base emission rate | 0.10% | Scheduled for one auction-update cycle |
| Standard tick | 10,000 OHM | Manager setting immediate; auction refreshed at update |
| 6-month reclaim | 99% | Unchanged |
| Minimum conversion-price scalar | 110% of market-price input | Unchanged |
| Minimum premium | 50% | Unchanged |
| Tick-size base | 2x | Unchanged |
| USDS deposit cap | 60 million USDS | Unchanged |

EmissionManager updates the auction every third authorized Heart call. Queuing
settings is not proof that the effective auction has changed. The tests exercise
the next update and read back its resulting period, rate, target and tick size.
They call the EmissionManager component as Heart; they do not simulate a complete
keeper Heart transaction. For that component test only, `getCurrentPrice()` is
stubbed with the actual PRICE-module value read at the pinned block before the
governance simulation. Governance time travel otherwise makes frozen external
oracle rounds stale. The lifecycle and holder-impact tests do not use this stub;
future live keeper execution and oracle freshness require separate verification.

The base emission rate is pacing, not a hard issuance or annual supply cap. This
proposal does not introduce an annual budget policy or additional fund transfers.

## Existing holders

Immediate reclaim reads the shared asset/period rate at execution time. Existing
three-month receipts reclaimed after the change therefore use 90%. Full redemption
does not apply that discount. An existing redemption's amount and redeemable date
remain unchanged. Cancelling a redemption returns receipts; a subsequent immediate
reclaim uses the updated rate. Six-month positions and their 99% reclaim setting
remain unchanged.

The fork regression fixture transfers existing three-month receipts from a holder
to a test-only user and starts redemption before simulating governance execution.
It checks the unchanged record, full-redemption balance delta, updated immediate
reclaim and cancellation followed by reclaim. No live holder transaction is sent.

fixture deliberately fails if the expected balance or initial reclaim setting has
changed; refresh and document the fixture rather than overriding token storage.

Run the repository's full build, lint and test gates before publication. Preserve

without fail-fast behavior, so its final exit status alone is insufficient evidence.

## Builder regression coverage

Builder-only tests call the public proposal runner with only construction enabled.
Mocked getter responses at the pinned fork model drift in the four unchanged
controls and the six-month reclaim rate. Exact custom-error reasons are checked.
Rate tests cover no pending change, cancellation at target, matching schedules,
conflicting delta/duration/direction, increasing/decreasing deltas and the maximum
representable current rate. Five parameterized tests each run 256 fuzz cases.
They inspect exact generated calldata and zero ETH value; they do not execute
synthetic rate configurations or prove live-state freshness.

## State-dependent construction

The builder reads current values and skips already-satisfied changes. It derives
the base-rate delta from the observed rate. Its assertions reject unexpected drift
in controls described as unchanged; it does not silently reset those controls.
These checks run during construction/simulation, not as additional on-chain guards
at eventual governance execution. Rebuild and compare the exact action payload
before submission and revalidate pending changes before execution.
